# KaivoFlow production and n8n gap review

**Review date:** 13 November 2026  
**Scope:** Targeted source inspection, existing JVM tests, and selected official n8n/Android/Google Play documentation. This is not an exhaustive review of every line, every n8n connector or every competing product. No Android build, device execution, penetration test, provider integration test or Play review was performed. Treat all Android integration as unverified. No implementation changes were made as part of this review.

> **Status update:** This audit predates [milestone 01](MILESTONE_01_RELIABILITY.md), which changes selected-Spark routing, event filters, in-process run ownership and whole-Flow retries. Those changes are not Android-verified; the remaining blockers still apply.

> **Further update:** [milestone 02](MILESTONE_02_TRANSFER_AI.md) adds structure-only import/export and shallow AI extraction type checks. Full backup, n8n import, Android verification and production blockers remain.

## Verdict

KaivoFlow is a prototype/source implementation, **not production-ready and not at n8n parity**. It has promising Android-first UX and tested pieces of a Flow engine, but key paths that users rely on appear broken, incomplete, or unsafe. The previously delivered audit and README should not be interpreted as evidence that the production pillars, security properties or Android functionality are complete. Specific corrections follow.

## Verification performed

- Inspected the node catalog, AI, scheduling, trigger dispatch, webhook, flow engine, persistence, credentials, network, manifest and prompt-to-Flow code; searched call sites and compared them with selected official documentation.
- Independently compiled and ran the Android-free `FlowRunnerTest`, `FlowValidatorTest` and `ValuesTest`: **41 tests passed** on the available JVM toolchain. These are additional to the previously reported 84 tests across nodes, schedule math, codec, canvas geometry and expression fallback, plus 34 JavaScript assertions. The aggregate is **125 JVM test executions**, not 125 tests of a built Android app. The suite counts were obtained across separate prior invocations and this invocation; they do not establish real-device behavior.
- The repo has no Gradle wrapper. Android, Compose, QuickJS integration, Room, WorkManager, Hilt, R8, app signing, 16 KB page alignment, live providers and Play compliance remain unverified.
- Individual source observations below are labeled as findings or risks. A static inspection is not a substitute for compiling and reproducing on-device.

## P0: release blockers discovered

1. **Empty manual and scheduled Runs can execute no downstream work.** `CanvasViewModel.run()` constructs `RunTrigger(kind = "manual")`; scheduled `FlowRunWorker` defaults to empty items. `RunTrigger` defaults to an empty list. `PassThroughTrigger` forwards empty input, while `FlowRunner.executeStep()` skips non-trigger Steps with no live upstream items. A simple manual/scheduled Spark → action can therefore skip the action. Add an explicit tick item or well-defined trigger semantics, then test manual and scheduled end-to-end. (`feature/canvas/.../CanvasViewModel.kt`, `core/work/.../FlowRunWorker.kt`, `core/engine/.../FlowRunner.kt`, `core/nodes/.../TriggerNodes.kt`.)

2. **Notification and SMS filters are configured but not applied in event dispatch.** `FlowScheduler.dispatchTrigger()` selects Flows by trigger type and `!disabled`, but does not examine app, text, title, regex, sender, or ignore-own-app options. The Spark executor is a pass-through. This can run the wrong Flow on sensitive data and may cause feedback loops through KaivoFlow's own notifications. Implement per-Spark matching, correct selection in multi-Spark Flows, and negative/privacy regression tests before enabling these Sparks. The listener comments and Privacy Centre language suggesting matching already occurs are misleading.

3. **Scheduling is not recurring as claimed.** Daily/weekly/monthly use one-time work tagged `TAG_RESCHEDULE`, but inspection found no consumer that schedules the next occurrence after the worker finishes. WorkManager constraints can delay execution; this is not an exact 08:00 guarantee. All scheduled work also requires a network connection even for offline-only Flows, and `cancel(flowId)` cancels all work tagged for that Flow, potentially including event Runs when a schedule is edited. `BootReceiver` ignores timezone/time-change actions listed in the manifest. Test repeat cycles, offline Runs, edit/disable, missed runs, timezone changes, reboot and OEM behavior. Android explicitly describes periodic work as inexact ([Android background task guidance](https://developer.android.com/develop/background-work/background-tasks/data-transfer-options)).

4. **Webhook is not integrated as a functioning Android service.** The manifest declares `WebhookServer` as a service, but the class is a plain injected Kotlin class, not an Android `Service`. No calls to `start()` or `refreshRoutes()` were found outside the class. Further code-level build risks include a missing `toImmutableMap` import and an unscoped `launch` in `handle()`. The listener binds all interfaces, authenticates only if an optional secret exists, and returns success before dispatch is durable. Its secret handling is inconsistent with a credential-reference picker and must be checked end-to-end. Do not expose it until it is redesigned, compiled and security-tested. A mobile phone behind NAT or asleep is not a reliable public endpoint: use an explicitly designed secure relay or self-hosted service if always-on ingress is needed.

5. **Run concurrency and cancellation are not implemented as described.** In `FlowEngine`, `activeRuns` is populated only if an optional scope is provided, and the mapped job is an empty placeholder rather than the executing job. Typical `runById` and manual calls omit that scope; `isRunning` and engine-level `cancel` therefore do not reliably control the Run. A check-then-register race also exists. The UI cancels its own `runJob`, but that does not fix background Runs. Implement atomic ownership of the actual execution job, policy for concurrent events, persistent cancellation and tests for simultaneous triggers.

6. **QuickJS timeout/isolation claims are unproven and potentially unsafe.** `QuickJsExpressionEvaluator` calls `FutureTask.cancel(true)` and closes the engine from a different thread on timeout, without evidence that interruption stops native execution or that cross-thread close is safe; a single-thread executor could remain occupied. The advertised hard timeout/sandbox cannot be assumed. Assess the exact QuickJS library API, use a supported native interrupt and memory limit or process isolation as appropriate, add malicious infinite-loop/memory-exhaustion tests and a fail-closed policy. `CodeNode` depends on the same evaluator. No sandbox escapes or crashes have been demonstrated; this is a serious design risk, not a confirmed exploit.

7. **Sensitive data and secrets can persist in unexpected places.** `JsonCodec.encodeFlow()` stores Step params and frozen output, while `encodeRun()` stores up to 20 output items per Step plus error strings. The Room DB shown is not database-level encrypted; the separate credential table uses Keystore-backed AES-GCM. Raw secrets are accepted as AI parameters and webhook/shared URLs may be params, so do not assume all secrets enter the vault. HTTP/provider errors and expressions can contain data or secrets, and the expression timeout logs source code. Audit all paths, use credential references only, encrypt sensitive content where appropriate, redact error/log/preview/export paths, and give users retention and clear-delete controls. Keystore hardware backing varies by device; the UI claim that every key lives in secure hardware is not established ([Android KeyInfo](https://developer.android.com/reference/android/security/keystore/KeyInfo)).

8. **Google Play permissions are a real gate.** The manifest always declares SMS permissions and `USE_EXACT_ALARM`, despite optional-feature language. Google Play lists device automation as a possible SMS exception, not an automatic approval; eligibility, declarations and actual use are subject to review. `USE_EXACT_ALARM` is restricted to qualifying alarm/timer/calendar core use cases. Remove restricted permissions from the default Play variant unless the product qualifies; use separately reviewed distributions/variants where justified. Do not assume notification access can be used to bypass SMS policy. See [SMS policy](https://support.google.com/googleplay/android-developer/answer/10208820?hl=en) and [permissions policy](https://support.google.com/googleplay/android-developer/answer/16558241). `SmsSparkReceiver` also treats `pdus` as a single byte array; standard SMS broadcasts carry multiple PDUs, so receiving must be implemented and tested correctly.

9. **Payloads and retries can lose or duplicate real actions.** `runNow()` puts the full serialized event in WorkManager `Data`; Android caps `Data` at 10 KB, much smaller than the webhook's 256 KB limit. Some dispatch errors are swallowed. `FlowRunWorker` retries failed Runs as a whole, so earlier irreversible actions can run again. Use durable payload storage referenced by ID, transactional enqueue/outbox, explicit delivery guarantees, event IDs/deduplication and idempotency keys. Surface failures and dead-letter events. See [Android Data](https://developer.android.com/reference/androidx/work/Data).

10. **Build and production pillars are not satisfied.** The current source was never assembled with Android Gradle Plugin. Packaging configuration alone does not establish 16 KB ELF/ZIP alignment; build and inspect an actual release AAB and run a 16 KB emulator. R8, JNI, provider parsing, foreground-service policy/timeout, battery tests, access disclosures and Data Safety form all require actual validation. Some imports/dependencies may fail beyond those identified above. The previous `LOGIC_AUDIT.md` describes fixes and limitations but is not a production sign-off.

## Import/export design: implement safely before n8n migration claims

1. Define a versioned native bundle envelope (schema version, app compatibility, Flow documents, optional resources, checksum). Save/open via Android Storage Access Framework. Default import must create a **disabled draft** and never execute code, make network requests, or register triggers.
2. Preview names, Step types, unsupported features, sensitive permissions, endpoints and credential requirements. Bound input bytes, nesting, number of Steps, decompression ratio and processing time; reject malformed input and path traversal. Assign fresh IDs or provide explicit collision policy; import transactionally with rollback.
3. Export credential **references only**, not secret values; scan/redact sensitive params, authorization headers, embedded URLs/tokens, test data, run outputs and personal content. Warn that arbitrary code/text cannot be guaranteed secret-free. Offer opt-in encrypted, authenticated full backups with independent recovery keys and clear restoration limitations; never silently export credentials.
4. n8n import is a translation project, not just reading JSON: versioned node type and parameter mappings, port/branch mapping, expression dialect, trigger semantics, error/retry behavior, node versions, authentication, binary data, code and subflow differences. Preserve unsupported nodes as disabled placeholders and report each unsupported operation/semantic mismatch; require explicit credential rebind and human review. Test with representative real n8n exports and compare outputs in a safe harness. Exporting back to n8n requires a separate compatibility map and honest loss report.
5. Test round trips, unknown versions, duplicate IDs, untrusted inputs, secrets in headers/URLs, canceled imports, device migration and failed credential restoration.

## AI design: strong, useful and controlled

- Provide explicitly selected providers: cloud/BYOK or genuinely on-device inference where supported. Ollama localhost is the phone itself, not a user's laptop; LAN access and cleartext/TLS compatibility need explicit configuration and testing.
- Flow-builder pipeline: user prompt → clarification → proposed typed graph and permissions/data destinations → schema and policy validation → editable diff → dry-run with simulated side effects → user approval → publish. Never silently invent addresses, location, credentials or actions.
- Agent runtime: typed tools with least-privilege scopes, allowlists, maximum iterations, time/token/cost caps, model fallback, tracing, secure memory and deterministic approval for sending messages, spending, deleting or changing data. Treat external content as untrusted; prompts are not security boundaries. n8n supports per-tool approvals ([n8n human review](https://docs.n8n.io/advanced-ai/human-in-the-loop-tools/)).
- Quality: regression datasets, schema conformance, adversarial injection tests, tool-call accuracy, cost/latency metrics and explicit human review. n8n documents evaluations and RAG; parity requires real implementations and measurable outcomes, not just another model selector ([n8n AI examples](https://docs.n8n.io/build/integrate-ai/ai-examples)).

## Recommended sequence and exit criteria

**Phase 0 — buildable baseline.** Add a verified Gradle wrapper and CI with JDK/SDK versions proven compatible with the pinned catalogue; compile debug and release, run lint and unit/instrumented tests, collect and triage failures. Exit: clean CI artifacts, installed release app, no unsupported claims. Do not silently change brief-pinned versions.

**Phase 1 — trust and core reliability.** Fix P0 empty triggers, matching, scheduling, cancellation/concurrency, SMS/permission variants, sensitive-data handling, evaluator containment, webhook design and WorkManager data/retry safety. Exit: automated integration tests plus real Android tests, no confirmed critical security issues, accurate disclosures and documented delivery guarantees.

**Phase 2 — portable and usable.** Native import/export and backup as above, searchable diagnostics, activation/disable control, versioned drafts, undo/redo, TalkBack, offline flows. Exit: safe round-trip and adversarial import tests on multiple Android versions.

**Phase 3 — meaningful n8n subset.** OAuth2 and a prioritized connector set, documented node-operation matrix, validated n8n importer, durable waits/checkpoints, stable APIs. Exit: golden end-to-end tests against actual provider sandbox environments and migration fixtures.

**Phase 4 — differentiated AI and mobile.** AI planner/repair, tool calling with approvals, evaluations and cost controls; Android-native approved triggers and capabilities. Exit: benchmarked workflows, adversarial safety evaluation and real-device UX/performance measurements.

**Phase 5 — optional always-on and enterprise.** If the goal includes public ingress, teams, high availability and operation while phones are offline, design an optional self-hosted or managed backend. Specify encryption, trust, data residency, sync/conflicts, operating costs, SLOs and compliance; preserve local-only mode. Benchmark against selected competitors and use cases rather than promise to be universally better.
